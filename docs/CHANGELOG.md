## [1.3.0] - 2026-10-23

### 四十六、合同履约：付款计划 / 验收 / 质保金，并纳入应收应付与报表

把合同从「一张留档台账」变成「钱从哪来、什么时候来」的凭据：
签订 → 付款计划（N 期）→ 验收 → 质保 → 期次收付款 → 应收应付 → 报表。

#### Added — 付款计划与期次收付款
- 新表 `inv_contract_plans`：期次、名称、类型（预付/进度/验收/质保金/其他）、
  比例、金额、约定日期、触发节点（签订/验收/质保到期）、已收付累计。
- **期次状态不落库**：未到期 / 待收付 / 部分 / 已结清 全部由金额差额与日期现算，
  与订单结算的口径一致，避免「已收满却显示待收付」这类漂移。
- 比例与金额联动：填比例按合同金额折算金额（合同金额改了金额跟着变），
  填金额则比例清空 —— 想按比例约定就填比例，想写死金额就填金额。
- 已发生收付款的期次：金额与比例不可改、不可删（后端拒绝，前端同步禁用）。
- 计划合计不得超过合同金额；质保金期次合计不得超过质保金金额。
- 收付款复用 `inv_settlements`（新增 `plan_id` / `source`），
  与订单结算同一张表、同一套并发防线（行锁 + 条件更新）。
- 全部期次结清且质保已了结时，合同自动置为「已完成」。
- 新接口：`POST /inv/contract-plans/settle`、`GET /inv/contract-plans/{id}/settles`。

#### Added — 验收与质保
- 合同新增 `accepted_at` / `accept_result` / `warranty_months` / `warranty_end_at` /
  `retention_rate` / `retention_amount`。
- `POST /inv/contracts/{id}/accept` 登记验收：验收日期、结论（合格/不合格/整改）、
  质保月数；质保到期日按「验收日 + 月数」算好落库（报表与筛选要在 SQL 里比这个日期）。
- **不新增状态码**：仍是 1 执行中 / 2 已完成 / 3 已终止，界面的
  「待验收 → 已验收 → 质保中 → 质保到期 → 已完成」由日期派生，历史合同零迁移。

#### Changed — 应收应付
- 应收 / 应付改为**两类来源合并**：已审核单据 + 合同未结清期次（终止合同不计）。
- 列表新增「来源」列与 `source` 筛选（order / plan）；合同行显示合同号 + 第几期。
- 汇总新增 `orderTotal` / `planTotal`（其中口径），页面标注「单据 X ｜ 合同 Y」。
- 合同行收付款走期次接口（批量收付款只对单据开放，勾选时合同行不可选）。
- 关键字可搜合同号与期次名（如「HT0007 验收款」）；导出新增来源/期次列。

#### Added — 报表
- 报表中心新增「合同执行」：合同金额、计划合计、已收付、未收付、质保金未收、
  履约阶段、质保到期，带合计行与导出（`GET /inv/report/contract`）。
- 新增「合同台账」：一行一笔实际发生的收付款，按日期倒序
  （`GET /inv/report/contract-ledger`）。
- 合同两个区不跟随页面顶部的时间范围（合同是跨期台账），自带阶段/类型/关键字筛选。

#### 权限
- 新增 `inv:contract:accept`（验收）、`inv:contract:settle`（合同收付款），
  与「录合同」分开授权：能录合同的人未必能确认验收、更未必能登记收付款。

#### 验证
- 接口冒烟 **328 项 0 失败**（新增 15 条：计划比例折算、计划超额拒绝、验收推进质保、
  质保到期日计算、期次收款与结清、超额收款拒绝、应收按来源筛选、合同执行报表、台账）。
- 端到端脚本另测 31 项（含「已收付款期次不可改金额/不可删」「有收付款的合同不可删」）。
- `go build ./...` / `vue-tsc --noEmit` / `vite build` 全部通过。

## [1.2.9] - 2026-10-23

### 四十五、合同管理模块 + 采购 / 销售 / 合同通用附件

#### Added — 合同管理（进销存 → 合同管理）
- 新表 `inv_contracts` + 权限码 `inv:contract:list / create / update / delete`，
  菜单位于「销售管理」之后、「库存管理」之前。
- 字段：合同编号（留空自动生成 `HT0001` 式流水，可手填 / 可改，重号拒绝）、
  名称、类型（采购挂供应商 / 销售挂客户）、往来单位、签订日期、
  履约起止（选填，结束不能早于开始）、金额、状态（执行中 / 已完成 / 已终止）、
  业务员、备注。
- **不把合同做成单据的强制上游**：一张合同常对应多张采购 / 销售单，也常先开单后补合同。
  单据上没有 `contract_id`，开单不需要先建合同；按合同核销应走统计查询。
- 列表支持关键字（编号 / 名称 / 往来单位 / 业务员）边输入边查、类型 / 状态 /
  签订日期区间筛选、导出 xlsx、打印；受数据范围约束（按创建人）。

#### Added — 业务附件（采购单 / 销售单 / 合同共用）
- 新表 `inv_attachments`（`biz_type` + `biz_id` 定位业务对象），文件落在
  `app.attachment_dir`（默认 `data/attachments`），库里只存元数据与相对路径。
- 接口：`POST /inv/attachments`（multipart，额外字段 bizType / bizId）、
  `GET /inv/attachments`、`GET /inv/attachments/count`（一次批量算角标）、
  `GET /inv/attachments/:id/file`（默认 inline，`?download=1` 强制下载）、
  `DELETE /inv/attachments/:id`。
- 入口在列表**操作列**：`附件(N)` —— 放在固定列里，窄屏横向滚动时也能点到。
- 安全与边界：
  - **扩展名白名单**（图片 / PDF / Office / 压缩包），单文件 20 MB；
    上传前用 `http.MaxBytesReader` 卡住请求体，写入时再 `io.LimitReader` 兜一次
    （客户端声明的 size 不可信）；
  - 磁盘用随机名、原始名只用于下载；`StoredPath` 不出现在接口里，
    读取时校验前缀防目录穿越；
  - MIME 按扩展名给（不信客户端 Content-Type）+ `X-Content-Type-Options: nosniff`；
  - 权限跟着单据走（能看单据才能看附件），越权一律 404 而不是 403；
  - 删除为软删，文件保留（可恢复），磁盘空间按目录整体回收。

#### Changed — 配置
- 新增 `app.attachment_dir`（默认 `data/attachments`，相对 exe 目录解析）。
- **部署注意**：附件目录不在数据库里，备份要连它一起备，否则会得到
  「记录在、文件没了」的半套数据（见 DEPLOY §7）。

## [1.2.6] - 2026-10-22

### 四十四、默认端口改为 6085、新增商品的多单位换算提示

#### Changed — 默认端口 6082 → **6085**
- 后端 `app.port` 默认 **6085**，交付包 `config.yaml`、`config.example.yaml`、文档示例、
  冒烟脚本默认地址同步。
- 前端 dev server 仍是 **6083**，`vite` 代理目标改为 `http://127.0.0.1:6085`。
- **升级不会改已部署机器的端口**：端口来自各机器自己的 `config.yaml`，
  想换就把 `app.port` 改成 6085 再重启（记得防火墙放行）。

#### Added — 多单位时的换算提示
- 新增 / 编辑商品时，单位小表下方实时显示换算关系：
  「`1 箱 = 10 个（库存按「个」计）`」，随单位名与换算率同步更新；
  尚未指定基本单位或单位名为空时，提示改为「勾选「基本」选定库存计数单位…」。
- **只在多单位时显示**：单组布局（1 规格 1 单位）连这一行都不渲染 ——
  那一个单位就是基本单位、换算率恒为 1，写「1 个 = 1 个」只是噪音。
- 换算率填错是「安静的错」（「2 箱」到底入账 2 还是 20，库存与单据会一起错），
  所以这行用 `text-secondary` 而不是 placeholder 级灰，保证读得到。
- 顺手修掉 `removeUnit` 的过时提示语（「系统会按「个」处理」——
  后端从 1.2.3 起就不再补默认值了）。

## [1.2.5] - 2026-10-21

### 四十三、库存管理改名与页签换位、销售 / 采购明细可按往来单位筛选并导出

#### Changed — 「出入库」菜单改名为「库存管理」
- 侧边栏标题 `出入库` → **`库存管理`**：这个页面管的是库存本身，出入库只是库存变动的一种方式。
- **存量部署自动跟进**：新增 `seed.menuRenames`，播种时只在标题仍是旧内置值（`出入库`）时改写成

- 两个页签换位：**库存查询在前、出入库单据在后**，进页面默认落在库存查询（先看现状，再翻历史单据）。

- `GET /inv/report/detail` 新增 `party` 参数，按**往来单位名模糊匹配**
  （销售 = 客户、采购 = 供应商）。明细卡片头右侧是筛选框，回车 / 点「查询」生效，清空即恢复全部。

#### Removed — 导出里两段死代码
- `exportPurchase`（采购分析，v1.2.4 已删该报表区）与 `exportInventory`（库存分析版式）
  已无调用方，连同 `ReportExport` 里对应的 `purchase` / `inventory` 分支一并删除，
  避免「传了 type 却悄悄落进 default」的假成功。

### 四十二、报表中心改版 + 规格单位默认一组 + 搜索边输入边查

#### Changed — 报表中心六个报表区

删掉「采购分析」「库存分析」两个报表区，改为：

| 报表区 | 内容 |

  服务端留了 1000 行保险丝。
- 新增 `GET /inv/report/stock-ranking`、`GET /inv/report/detail?biz=sales|purchase`。
  明细返回 `rows/total/amount/qty/truncated`，超过 2000 行时页面明示「仅展示前 N 行」；

#### Changed — 商品规格单位默认只有一组

新增商品时把「1 个规格 + 1 个单位」压成一行（规格 / 单位 / 换算率 / 预警 +
「添加单位 / 添加规格」），不再先摆「规格 1」卡片再摆一张带表头的单位小表。
点添加后自动切回分块布局。

#### Changed — 开单商品下拉不再带规格数量

`名称（编码）· N 个规格` 改为 `名称（编码）`（有余量时保留参考价后缀）：
明细行后面本来就有「规格」「单位」两列，塞进商品名只会让每行更长、更难扫。

#### Changed — 关键字录入即查询

所有列表页（采购 / 销售 / 出入库 / 库存查询 / 应收应付 / 商品 / 客户 / 供应商 /
打印模板 / 用户 / 角色 / 菜单 / 部门 / 操作日志 / 登录日志）的关键字框
绑 `@input` + `useDebouncedSearch`（防抖 320ms）：输入停顿后自动查询，不必按回车；
回车与「查询」按钮仍然有效。

#### Changed — 批量收付款按钮常显

「批量收款 / 批量付款」不再等勾选才出现：按钮常驻，未勾选时禁用，
勾选后在按钮上带张数。

## [1.2.3] - 2026-10-21

### 四十一、应收应付批量收付款 + 规格单位排版重做 + 开单参考价可见

#### Added — 应收应付批量收付款

表格加勾选列（已结清的行不可勾），工具栏出现「批量收款（N）／批量付款（N）」，
弹窗只填结算方式 / 日期 / 备注，金额按每张单据的**未结余额**各记一笔。

新增 `POST /inv/finance/settlements/batch`（权限 `inv:finance:settle`）：

- **整批原子**：任一张未审核 / 已结清 / 余额被改动，整批回滚 ——
  批量付款「付了一半」比完全没付更难对账；
- 结算前对涉及的订单 `SELECT … FOR UPDATE`，并发双击不会超额；
- 同一单据传两次只结算一次（入参先去重）；
- 可选 `amounts` 按单据指定金额（个别只付一部分），缺省即结清。

#### Changed — 商品「规格与计量单位」重排

- **单位小表改固定列宽**（单位 220 / 换算率 120 / 基本 64 / 价格 118 / 删除靠右）：
  原来两列按比例分掉整行，看着空旷；现在是一条直线，展开价格也不挤前面的列。
- 去掉整段的说明文字、换算率下方的「1 箱 = 10 个」提示、输入框占位提示；
  表头由「计量单位 / 基本单位」简化为「单位 / 基本」，删除按钮只留图标。
- 去掉单位表那 8px 左缩进（它让表格比规格名输入框往里缩一截，像错位）。

#### Changed — 规格 / 单位**留空就是空白**

后端 `normalizeSpecs` 不再把空名补成「默认」「个」（旧行为），空名原样存空串：

- 仍然保证结构完整：至少一条规格 + 一个单位，换算率缺省 1，第一个单位提为基本单位；
- 名称判重只看非空值；空名也占一个坑（`(product_id, spec)` / `(spec_id, unit)`
  是唯一索引），所以「两个空规格」会返回「同一商品下只能有一个未填名称的规格」，
  而不是一条 500；
- 空名称在列表摘要、开单规格下拉、商品展开行显示为「—」。

#### Fixed — 开单选中商品没有带出参考价

- **商品下拉里直接显示参考价**（`参考进价 ¥88.00` / `参考售价 ¥99.00`），
  选之前就能看见会带出什么价；
- 补掉一处取价竞态：开单弹窗是异步重拉商品档案的，用户手快（刚建完商品就开单）时
  那一瞬间档案还没到，`applyPrice` 找不到商品会把单价留成 0；
  现在档案到位后对「单价仍为 0 且已选商品」的行补一次取价；
- 取价优先级不变：商品级参考价（>0）→ 该单位的采购价 / 销售价。

## [1.1.5] - 2026-10-20

### 三十三、pg_dump / pg_restore 自动探测扩展到全盘符

部署机把 PostgreSQL 装在 D 盘（安装向导允许选盘符）时，原先只探测系统盘

- 多版本共存时仍自动选**版本最高**的客户端；
- 「找不到 pg_dump」的提示同步修正配置键名（`backup.pg_dump_path`）。

#### 效果

标准结构安装（任意盘符）或已加入 PATH 的机器，备份/恢复**零配置**可用；
确实装在非标准路径时才需要手工填 `pg_dump_path` / `pg_restore_path`
（注意 YAML 双引号内必须用正斜杠 `/`，反斜杠 `\` 会被当成转义序列导致解析失败）。

冒烟用例「客户行含余额与单据数」暴露出一个状态机定义上的偏差：

#### Fixed

- **时区库缺失导致连不上数据库（交付级）**：`time.LoadLocation("Asia/Shanghai")`

### 三、审查与易用性（第三轮）

对全项目做了一轮 bug 与逻辑审查，并顺带优化进销存的操作路径。

#### Fixed — 越权（P0）

- **跨业务线的写操作越权**：`/inv/orders` 路由的 `RequirePerm` 是「采购或销售任一」，
  handler 里的业务线二次鉴权只检查「持有 `inv:<bizType>:` 前缀的任意权限」。
  于是持有「`inv:purchase:list`（采购只读）+ `inv:sales:finish`（销售审核）」的账号
  **可以审核 / 删除采购单** —— 越权不需要绕过中间件，只要权限码拼得够巧。
  现在读路径仍走宽松口径，写路径改为比对完整的 `inv:<bizType>:<action>`
  （`ensureBizPermAction`）。冒烟新增「采购只读 + 销售审核」账号的越权矩阵断言。

#### Fixed — 并发（P1）

- **并发审核会重复过账**：`OrderChangeStatus` 在事务外读状态、判「不是已审核就放行」，
  两次并发都会读到「待处理」，于是生成两张出入库单、扣两次库存，
  而界面上只看到一张单。改为**条件更新** `WHERE id = ? AND status <> ?`
  并放在事务最后，`RowsAffected == 0` 即回滚整个事务。
- **并发作废会重复回滚库存**：`StockOrderVoid` 同样问题，改法同上。

#### Fixed — 静默的错误结果（P1）

- **`ProductPick` 静默截断**：一次最多 500 个商品，超出的不返回也无提示，
  用户只会以为「系统没录这个商品」。返回体改为 `{ items, total, truncated }`，
  前端 `truncated=true` 时提示「请用关键字搜索」，并把 `el-select` 接上
  `remote` + `remote-method`（服务端结果**合并**进本地列表，不替换 ——
  替换会让已选好的行找不到自己的 specId、显示成空白）。
- **模糊搜索未转义 `%` `_`**：搜「`M12_40`」会连「`M12X40`」一起出来，
  搜「`50%`」等于搜 `50` 开头的一切；结果既不报错也不为空，只是**不是你要的那批**。
  12 处 `ILIKE` 统一走 `likeKW()` 转义 + `ESCAPE '\'`。

#### Fixed — 数据一致性（P2）

- **停用挡不住**：`resolveSpecUnits` 只校验三元组存在、不校验状态，
  页面打开后管理员停用档案这段竞态里，库存仍会记到已停用规格上。
  现在三层（商品 / 规格 / 单位）都必须启用，错误信息点名是哪个。
- **规格名可带首尾空格**：`saveSpecs` 按 trim 后的名字比对、却写入未 trim 的值
  （`saveUnits` 一直是 trim 的，两处不一致）。统一写入 trim 后的值。

#### Changed — 易用性

- **商品筛选的分类下拉改为全量**（含已停用）：只给启用分类的话，
  分类一停用，属于它的那批商品就再也筛不出来 —— 筛选器变成「看起来正常但永远筛不到」。
  表单里的下拉仍只给启用项，但会把当前值补回去（改为在打开弹窗时缓存，
  不再依赖列表行还在不在 —— 翻页后就拿不到了）。
- **规格可以单独启用 / 停用**：被单据引用过的规格删不掉只能停用，
  此前没有这个开关，想让它退出新单据却无从下手。
- **分类删除不再让用户去撞 409**：引用数 > 0 时直接弹窗说明为什么不能删、
  该怎么做（移走商品或改为停用），而不是弹确认框让人点了才被拒。
- **单据与出入库明细的商品下拉支持远程搜索**（输入编码 / 名称直接搜）。

### 四、第四轮补扫（同类问题继续揪）

上一轮按「越权 / 并发 / 静默错误」三条线排查后，又补扫了一遍，发现并修掉 4 处
**同一条线延伸出来的漏网之鱼**：

- **[并发] 登记收付款也会超额结算**：`Settle` 与审核同病 —— 事务外读 `settled_amount`
  校验，两个并发登记都通过，累加后 `settled_amount` 顶破 `total_amount`。
  改为事务内条件更新 `settled_amount + ? <= total_amount + 0.001`，0 行即回滚。

  （缩进不同），客户分支仍是裸 `ILIKE`。已补上，并加冒烟断言钉住

- **[口径不一致] 概览预警数把停用商品算进去**：`WarnProductCount` 只查规格表、
  没联商品状态，商品停用后其规格仍可能留在启用态被计入。改联表过滤启用商品。
- **[口径不一致] 商品列表展开行的预警不排除停用规格**：`buildSpecVOs` 的 `Warn`
  未看规格 `status`，与 `Inventory` / 概览口径不一致。统一为「启用才预警」。

#### 实现备忘

- zip 用 Node 直写（store 模式 + UTF-8 文件名标志 + 自实现 CRC32）：项目没有 zip 依赖，
  Windows 也未必有 zip/7z。升级包不追求压缩率，store 足够。

### 二十三、运维加固第三批（P3×10：架构洁癖与运行时弱点）

扫描出的 10 项 P3 全部收口。共同主题：**框架层不该知道业务**、**同一件事只有一份实现**、
**长任务不要被默认 20 秒误杀**、**危险动作拆成独立钥匙**。

#### Fixed

- **框架层去掉业务表硬编码**：`internal/ops` 的巡检关键表与备份锚点表不再写死 `inv_*`，
  改为 `CheckOptions.KeyTables` / `BackupOptions.AnchorTables` 注入，缺省只锚定框架表 `sys_users`；
  业务表清单由应用层 `module/ops` 传入。框架层不 import 业务模块，也不硬编码业务表名。
- **拆 `ops:reset` 权限点**：业务数据清理（整表清空账本 / 重置数据库）与日志清理分开授权。

  「能清日志」不再等于「能重置数据库」。
- **删除 `UpgradePlan` 死字段**：`staging`、`manifest` 两个赋值后从未读取的字段移除。
- **`verifyArchive` 不再静默放行**：找不到 `pg_restore` 时记告警日志，并把 `verified=false`
  写进备份元数据，前端备份列表加「校验」列提示「未校验」。
- **巡检不暴露绝对路径**：`Check.LatestBackup` 由绝对路径改为文件名，`ops:list` 不再把服务器

- **长任务放宽前端超时**：备份 / 恢复 / 清理 / 升级 / 上传 / 下载统一 10 分钟超时，

- **锁定 `internal/ops` 别名约定**：`module/ops` 与 `internal/ops` 包名同为 `ops`，
  补包注释锁定「引用本包必须用 `fwops` 别名」，防未来裸 import 撞名。
- **统一备份时间戳两份实现**：CLI（Split 版）与列表（正则版）各写一份，而 Split 版对

- **切换清理范围清空残留**：前端切换业务清理范围时复位 `bizResult` 与「清零库存」勾选，

- **升级包解压流式化**：`readZipFiles` 不再把 backend/frontend 整段读进内存，改为
  `openPackage`（manifest 读内存，大文件只登记 zip 条目）+ `writeZipEntry`（边写 staging

### 二十二、运维加固两批（升级状态机 / 幂等 / 上传限长 / 备份撞名 / 配置校验 / 清理白名单）

全项目扫描出的 16 项发现里，P1 两项与 P2 四项在这一轮修完。共同特点是：
**测试环境跑不到，现场才会踩**——所以每一条都补了「运行时判据」而不是只靠文档约定。

#### Fixed（P1）

- **纯前端升级包被误判失败**：`FinalizeUpgrades` 一律拿「当前版本 vs 目标版本」比对，
  但纯前端包不需要重启，版本永远不等 → 每次都标 `failed`。改为执行阶段就定去向
  （`upgradeOutcome`）：`manifest` 里没有 `backend` 的直接 `success`，有才进 `applied`。
- **执行升级可并发双跑（TOCTOU）**：原逻辑先 `First` 读 pending 再无条件 `Updates`，
  两个请求能同时进来。改为 `WHERE status = 'pending'` 的抢占式更新，抢不到就拒绝；
  新增 `executing` 中间态，崩溃遗留的记录重启时判为「执行中断」（`failed`）。
- **运维写接口无幂等**：`/ops` 路由组挂幂等中间件（不带 `Idempotency-Key` 的请求照旧放行），
  前端 6 个写操作统一发键，冒烟补「同键重放、备份数只 +1」断言。

#### Fixed（P2）

- **上传升级包先落盘再限长**：`c.FormFile` 内部会把超过 32 MB 的部分写到临时文件，
  事后 `LimitReader` 只能「发现」超限。改为在解析前用 `http.MaxBytesReader` 卡住请求体
  （512 MB + 4 MB multipart 余量），超限在读的阶段就断开。600 MB 包实测 2.2 s 被拒。
- **备份同一秒撞名互相截断**：文件名只到秒，两次并发写同一个 target 会产出
  「看起来存在、恢复才发现坏」的备份。落盘前 `O_EXCL` 原子占位，撞名报错而非覆盖；
  占位后任何一步失败都删掉空壳，不留 0 字节的假备份。
- **`upgrade.frontend_dir` 无校验**：配成 `.` / `/` / 可执行文件所在目录（及其祖先）时，
  升级的「改名旧目录」一步会把程序自己脚下搬走。改为启动期拒绝这三类值（含 `staging_dir` 根）。
- **清理白名单不按档位判定**：`isAllowedBizTable` 只看「是不是框架表」，于是日志表
  在任何档都被放行（只是恰好没有档登记它）。改为带 `scope` 入参：日志表仅 `database` 档放行。

#### 测试

- 新增单测：升级去向（纯前端 / 含后端 / 失败优先）、`executing` 计入未收尾、
  限长错误识别（`*http.MaxBytesError`，不误判磁盘满）、备份占位撞名、
  `frontend_dir` 三类危险值、白名单按档位（9 组用例）。
- `go test ./...` 全绿；冒烟 **293 项全过**（含新增幂等回放 3 条）；
  真机验证：600 MB 上传被拒、`frontend_dir` 三类值启动失败、并发备份报「已存在」。

### 二十一、业务数据清理（清单据 / 清进销存 / 重置数据库）

上一轮的「数据清理」只覆盖日志与幂等键，业务数据（单据、商品、往来单位）一条都不碰。
但「把单据全清了只留商品」「演示环境复位」「把系统交给下一个使用者」这类需求真实存在，
于是补上**业务数据清理**——刻意做成另一套语义，而不是往日志清理里加参数。

#### Added

- **三档清理范围**（`internal/ops/bizcleanup.go`，命令与管理页同源）：

  | 范围 | 删什么 | 保留 |
  | --- | --- | --- |
  | `inv_documents` | 采购/销售/出入库单据与明细、收付款 | 商品、规格、单位、分类、客户、供应商、打印模板、框架 |
  | `inv_all` | 全部进销存业务表（含档案） | 系统框架 |
  | `database` | 全部进销存表 + 操作日志 + 登录日志 + 幂等键 | 系统框架（账号/角色/菜单/权限/部门/结构版本/升级记录） |

  「数据库重置」**刻意不动系统框架**：账号/角色/菜单删掉后系统立刻失去登录与鉴权依据，
  现场现象是「所有人都登不进去」，分不清是数据丢了还是系统坏了。
  真要连框架一起清，请直接 DROP DATABASE（程序会重新建库播种）。
- **`nova-ops reset` 子命令** + 管理页「数据清理 → 业务数据清理」区：
  范围卡片（删什么/留什么/当前行数）、逐表行数预览、库存勾选项、
  回滚点新鲜度提示与「先备份」按钮。
- 接口：`GET /ops/cleanup/scopes`（范围 + 行数预览）、`POST /ops/cleanup/business`（执行）。

#### 安全设计（三道闸门，都有测试）

1. **24 小时内必须有备份** —— 没有回滚点不许动账；命令行要 `--force` 才能跳过。
2. **确认口令与范围绑定**，三档互不相同（确认清理单据 / 确认清空进销存 / 确认重置数据库）——
   口令相同的时候，手滑点到「确认」就能从清单据跳到重置数据库。
3. **一个事务**：全部删除要么都成要么都不成，不会留下「单据没了但收付款还在」的库。

框架表（账号/角色/菜单/权限/部门/结构版本/升级记录）在任何范围下都不出现，
由 `TestBizCleanupNeverTouchesFrameworkTables` 钉住；日志表只允许出现在 `database` 档。

#### Changed

- 业务清理是**硬删**（软删会把行留着继续占唯一索引与主键），表被清空后 `setval`
  重置自增序列，下一单从 1 开始。
- 库存是勾选项而非默认动作：清单据时默认**不动** `inv_product_specs.stock` ——
  重录单据的人要清零，刚盘点完的人不能清，两种场景都存在。
- `database` 档会连操作日志一起清掉，所以除操作日志外另往应用日志写一条摘要
  （范围、总行数、是否清零库存），「谁在什么时候清了多少行」必须留得下来。

#### 测试与真机验证

- 新增 `internal/ops/bizcleanup_test.go`：口令互异、框架表免疫、日志表只在 database 档、
  删除顺序子表在前、未知范围报错带合法值、备份闸门三种情形。
- 真机（PostgreSQL 17.6，**在恢复出的临时库上跑，不碰生产库**）：
  `inv_documents` 删除 762 行、库存清零 183 行、序列重置为 1，
  商品/客户/框架表原样保留；再跑 `database` 档删除 3195 行，
  框架表（users 163 / roles 92 / menus 68 / depts 3 / schema_versions 2）全部保留。
  口令错误、未知范围、只读账号 403 均按预期拒绝。临时库已 DROP。
- api-smoke 280 → **290 项**。

### 二十、系统运维中心（管理页）+ 系统升级功能落地

上一轮把备份 / 清理 / 升级做成了 `nova-ops` 命令行，这一轮把它们接进后台，
并补上真正缺的一块 —— **系统升级功能**（此前只有文档里的 SOP，系统里没有入口）。

#### Added

- **「系统运维」页**（`/system/ops`，系统管理下第 6 个页面），四个页签与 OPS.md 章节一一对应：
  - **备份管理**：备份列表（文件名 / 时间 / 大小 / 表数 / 摘要）、立即备份、下载、删除、恢复演练弹窗；
  - **数据清理**：保留天数可调、预演（默认）、真删需输入「确认清理」；
  - **系统巡检**：库 / 结构版本 / 体积 / 最近备份 / 日志与幂等键统计 + 告警列表 + 关键表统计；
  - **系统升级**：版本三元组 + 四项预检 + 上传升级包 → 升级前备份 → 执行升级 → 重启生效，
    以及升级记录表。
- **后端运维模块** `internal/module/ops`（13 个接口，权限点 `ops:list` / `ops:backup` /
  `ops:restore` / `ops:cleanup` / `ops:upgrade`）：
  备份、恢复、清理、巡检四类动作各自独立授权 —— 备份只读、恢复建库、清理不可逆、
  升级替换程序，影响面完全不同，合成一个「运维管理员」等于逼着把全部权限发给同一个人。
- **`sys_upgrade_records` 升级记录表** + 四级状态机
  `pending → applied → success / failed`，结构版本 bump 到 **v2**。
- **系统升级功能**（`internal/ops/upgrade.go`）：
  - 上传升级包（zip）→ 校验 zip 结构（不许嵌套目录）、manifest 必填项、
    **文件名必须是纯 basename**（带路径可越出暂存目录写文件）、逐项 sha256；
  - 生成升级计划（动作清单摊开给人看）并落库；
  - 升级前**强制留档备份**，`apply` 会检查那份备份真实存在 —— 「没有回滚点不允许升级」在代码里落地；
  - 执行：后端二进制落位为 `<exe>.new`（Windows 不允许覆盖正在运行的 exe），
    前端产物原子切换（先解 `.new` → 旧目录改名 `.old.<时间戳>` → 切换，失败则把旧目录还回去）；
  - 启动时 `FinalizeUpgrades` 用**当前运行版本**与目标版本比对，一致才标 `success`，
    否则 `failed` 并说明原因。执行完直接标成功会让「升级完成」变成假消息。
- 配置新增 `upgrade.frontend_dir` / `upgrade.staging_dir`，以及 `app.release`
  （程序发布版本号，与 `app.version` 这个 API 版本段是两件事；建议构建时 ldflags 注入）。

#### Changed

- `internal/ops.Cleanup` 自己兜底保留期默认值（180 / 180 / 7 天 + 锁定窗口）：
  此前只有命令行做了 `firstPositive` 换算，**HTTP 接口传 0 会退化成「删掉此刻之前的全部记录」**——
  对操作日志那就是清空审计。同一道安全约束不能只依赖某一个调用方记得传对。
- 内置角色授权命名空间加入 `ops`：超管全量、系统管理员全量（五个点里没有 `:delete`）、
  只读访客只有页面。若现场要把升级权单独收给超管，从 `frameworkNamespaces` 摘掉即可。

#### 测试与真机验证

- 新增 `internal/ops/upgrade_test.go`（manifest 路径穿越 / 嵌套目录 / 计划 ID 稳定性 /
  动作清单 JSON 往返）与 `internal/module/ops/service_test.go`（备份时间戳解析、
  确认口令精确匹配、动作清单容错、待升级判定）。
- 新增 `TestCleanupDefaultsGuardAgainstZeroDays`：默认值必须为正，且边界必须早于「现在」。
- 真机端到端（PostgreSQL 17.6）：上传冒烟升级包 → 未备份时 `apply` 被拒 → 升级前备份 →
  口令错误被拒 → 执行升级（`applied`，`.new` 落位）→ 重启后记录被标 `failed`
  （运行版本 `dev` ≠ 目标 `9.9.9-smoke`）—— 生效核对链路符合预期。
  另验证：接口方式备份（23 张表）、清理预演、口令错误时按预演兜底不删数据、
  恢复演练恢复到临时库并核对行数。测试产物（`.new` / 暂存目录 / 临时库 / 冒烟记录）已全部清理。

### 十九、数据库备份 / 数据清理 / 系统升级（运维方案）

这块此前完全靠「记得手工 `pg_dump`」，没有保留策略、没有恢复演练、没有版本闸门 ——
真出事时能不能恢复全凭运气。现在补成一套**可执行 + 可验证**的方案，
详见 [`OPS.md`](OPS.md)。

#### Added

- **`nova-ops` 运维命令**（`backend/cmd/ops`，独立二进制，配置驱动、不跑迁移不播种）：

  | 子命令 | 作用 | 安全侧默认值 |
  | --- | --- | --- |
  | `backup` | `pg_dump` 自定义格式全量备份，写完**回读归档**校验，再按保留策略轮转 | `--no-prune` 可跳过轮转 |
  | `restore` | 恢复到**新库**（默认 `<db>_restore_<时间戳>`），恢复后核对表数与行数 | 必须 `--yes`；指向生产库还要 `--force` |
  | `cleanup` | 按保留期清理操作日志 / 登录日志 / 过期幂等键，**批删除** | **默认 dry-run**，`--apply` 才真删 |
  | `check` | 体检：结构版本、库体积、日志与软删除堆积、备份新鲜度 | `--strict` 有告警时退出码 1（给监控用） |

- **备份保留策略**（`backup.keep_count` 默认 30 份 + `backup.keep_months` 默认 6 个月）：
  既留最近 30 份，又保证最近 6 个月每月至少一份月档。
  只按「份数」会在长期停更后把唯一的旧档挤掉，只按「月份」又会在高频备份下爆盘。

#### Fixed — 表单标签宽度从来没生效（根因在按需导入）

统一过程中量 DOM 才发现：`label-width="76px"` **一直是失效的** ——
标签实际宽度等于文字宽度（三字 42px、两字 28px），所以同一行里输入框的起点各不相同。

根因不在表单本身，在按需导入的解析器：

- element-plus 2.x 把 `form-item` 拆成了独立组件，**样式是独立文件**
  （`components/form-item/style/css` → `el-form-item.css` 里有 `display:flex` 与标签宽度规则）；
- 而解析器把 `el-form-item` 映射到了父 barrel `form`，只引了 `form/style/css`
  （`el-form.css` 里没有那条基础规则）；
- 于是组件能渲染、样式缺席：`.el-form-item` 退化成 `display:block`，标签成了行内元素，
  `width:76px` 直接被忽略 —— 所有表单都是「标签在控件上方」，只是看着不难看，没人发现。

修法：解析器在「子组件只有 style 目录、没有自己的 index」时**同时引两份样式**
（父 barrel 的 + 子组件自己的）。这条不是给 form-item 打的补丁，
`radio-button` / `checkbox-button` / `timeline-item` / `step` 等同一形态的子组件一起修好了。

顺带补了 `.filter-form .el-form-item__label { flex: 0 0 auto }`：
标签在 flex 行里默认会被压缩，哪怕宽度写对了也会被内容挤窄。
