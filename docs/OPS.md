# nova-erp 运维方案：数据库备份 / 数据清理 / 系统升级

> 版本：v1.0（2026-10-18）
> 适用：单机部署的 nova-erp（PostgreSQL 13+，实测 17.6），日均写入几百到几千行。
> 本文既是**方案**（为什么这么做），也是**操作手册**（照着敲什么命令）。
> 结构变更明细见 [CHANGELOG.md](CHANGELOG.md)，日常操作见 [GUIDE.md](GUIDE.md)。

---

## 0. 一页看懂

| 事项 | 做法 | 频率 | 命令 |
| --- | --- | --- | --- |
| 全量备份 | `pg_dump` 自定义格式 + sha256 + 元数据，自动轮转 | 每日 22:00 | `nova-ops backup` |
| 升级前备份 | 同上，标 `--no-prune` 单独留档 | 每次升级前 | `nova-ops backup --no-prune` |
| 恢复演练 | 恢复到临时库，核对表数与锚点行数 | 每月 1 次 | `nova-ops restore --file … --yes` |
| 数据清理（日志） | 日志按 180 天、幂等键按过期 +7 天，分批删除 | 每月 1 次 | `nova-ops cleanup --apply` |
| 数据清理（业务） | 清单据 / 清进销存 / 重置数据库，硬删不可逆 | 按需 | `nova-ops reset --scope … --apply` |
| 体检 | 结构版本 / 体积 / 日志膨胀 / 备份新鲜度 | 每日 | `nova-ops check --strict` |
| 系统升级 | 备份 → 换二进制 → 启动自动迁移 → 冒烟 | 按需 | 见 §4.3 |

**三条不变量**（任何时候都不能破）：

1. **没有当天备份，不允许升级**。升级失败最坏的结果是回滚二进制，但只要结构动过，回滚就必须靠备份。
2. **旧程序不允许连新库**。由 `sys_schema_versions` 闸门强制，见 §4.2。
3. **业务数据只归档不删除**。清理只碰日志与幂等键；单据、明细、库存流水一律不自动删。

### 0.1 两条路径：命令行与管理页

同一套能力有两个入口，**底层是同一份代码**（`internal/ops`），不存在「脚本一套、界面一套」的漂移：

| 路径 | 适合谁 | 入口 |
| --- | --- | --- |
| `nova-ops` 命令行 | 运维人员、计划任务、无人值守 | `backend/cmd/ops` |
| **系统运维中心**（后台「系统管理 → 系统运维」） | 不懂命令行的决策者、临时处置 | `/system/ops` |

页面四个页签与本文章节一一对应：备份管理（§2）、数据清理（§3）、系统巡检（§5）、系统升级（§4）。
界面上刻意保留的几道闸门与命令行一致：清理默认预演、真删需输入「确认清理」；
升级必须先在页面上做「升级前备份」，否则「执行升级」按钮不可点。

> 恢复演练在界面上**只能恢复到新库**（覆盖生产库需停机后 `nova-ops restore --force`）——
> HTTP 接口不该提供「一次误点就盖掉生产库」的能力。

## 1. 现状与风险

先看清「现在是什么状态」，方案才有落点。

| 方面 | 现状 | 风险 |
| --- | --- | --- |
| 备份 | 无自动备份，全靠人记得手工导出 | 硬盘坏了 / 误删库 = 全部数据丢失，且**没有可回滚的时间点** |
| 迁移 | 只靠 GORM `AutoMigrate` 补齐表与列 | 它不知道库比程序新还是旧：回滚旧程序会安静地读错字段 |
| 日志 | 只能从页面「清空」（全量或无边界），无保留期 | 日积月累，最后要么不敢删、要么一刀切删光审计 |
| 恢复 | 从未演练 | 「备份成功」与「备份能恢复」是两件事，只有演练能区分 |
| 巡检 | 无 | 磁盘满、备份停了、日志爆量，都要等出事才发现 |

当前基线（本机实测，用于容量规划）：

| 指标 | 数值 |
| --- | --- |
| 库体积 | 12 MB（23 张表） |
| 操作日志 | 2141 行 / 约 2 天（开发期压测产生） |
| 单据 | 161 张 / 明细 283 行 |
| 单次全量备份 | 165 KB / 约 1 秒 |

按生产每天 200 张单据、3000 条操作日志估算：**一年约 150 MB，十年不到 1.5 GB**。
这个量级决定了：不需要分库分表、不需要增量备份、不需要归档库 —— 每日全量 + 月档就够，
**方案要做的是「一定会发生」，不是「理论上最优」**。

## 2. 数据库备份

### 2.1 目标

| 指标 | 取值 | 理由 |
| --- | --- | --- |
| **RPO**（最多丢多少数据） | ≤ 24 小时 | 进销存是「当天开单当天录」，最坏情况是重录一天的单据（纸质单据还在） |
| **RTO**（多久恢复服务） | ≤ 30 分钟 | 备份 165 KB～几十 MB，`pg_restore` 秒级到分钟级；人工操作占大头 |
| 保留 | 最近 30 份 + 最近 6 个月每月 1 份 | 覆盖「昨天改错了」和「上个月对账发现少一笔」两类场景 |

> 如果业务要求 RPO ≤ 1 小时，再上 WAL 归档（§2.8），**不要**在没有需求时先上 ——
> 它要求开 `archive_mode`、维护归档目录、定期 `pg_basebackup`，运维成本翻倍。

### 2.2 三层备份

| 层 | 触发 | 目的 | 保留 |
| --- | --- | --- | --- |
| 日备 | 计划任务每日 22:00 | 日常回滚点 | 最近 30 份 |
| 升级前 | 人工执行，`--no-prune` | 升级失败时的唯一退路 | 每版本 1 份，手工管理 |
| 月档 | 日备自动产生（每月最新那份不删） | 长期追溯 | 最近 6 个月 |

### 2.3 命令与产物

```bash
# 在 backend/ 目录下执行（config.yaml 同目录）
./nova-ops backup --config config.yaml
```

一次备份产出三个文件，**三个都要一起拷走**：

```
backups/nova_inv_v5-20261018-100717.dump          # pg_dump 自定义格式（压缩、可选择性恢复）
backups/nova_inv_v5-20261018-100717.dump.sha256   # 摘要，恢复前自动校验
backups/nova_inv_v5-20261018-100717.dump.json     # 元数据：库名/版本/耗时/表数/锚点行数
```

设计上的几个刻意选择：

- **自定义格式（`-Fc`）而不是纯 SQL**：自带压缩、能只恢复某张表、恢复时并行建索引。
  纯 SQL 只能整库重放，且几万行 `INSERT` 慢一个数量级。
- **写完立刻回读**：备份完成后用 `pg_restore --list` 读一遍归档目录。
  `pg_dump` 退出码为 0 不代表文件完整（磁盘写满会截断），而「备份是坏的」只有等到出事那天才会发现。
- **半截文件当场删掉**：占位之后任何一步失败（pg_dump 报错、归档回读为空、
  算摘要失败）都把文件删掉。留着半截/空壳文件比没有文件更危险 —— 它会让人以为有备份。
- **同一秒只能有一份**：文件名只到秒，两次备份落在同一秒会写同一个文件、
  互相截断成两份都不可恢复的坏备份。落盘前用 `O_EXCL` 原子占位，
  撞名直接报「同一秒内已有备份在生成」，而不是默默覆盖（管理页连点、
  定时任务与手工备份撞车时就会遇到）。
- **口令走环境变量**：`PGPASSWORD` 传给子进程，不出现在命令行里（`ps` / 任务管理器对同机所有用户可见）。

### 2.4 保留策略

```
最近 30 份（约一个月）  ──┐
                          ├─ 保留
最近 6 个月，每月最新一份 ──┘
其余删除（连同 .sha256 / .json）
```

两条硬约束（代码里钉死，有单测）：

- **最新一份永不删除**：参数写错（`keep_count=0`）也不会把唯一备份删掉；
- **同一时间戳的结果稳定**：不会出现「这次删 A、下次删 B」。

轮转只删 `backups/` 目录里匹配 `<db>-<时间戳>.dump` 的文件，不碰别的文件 ——
不要把其它资料放进备份目录。

### 2.5 存放位置（这一条最容易被忽略）

**备份和数据在同一块盘上，等于没有备份。**

| 位置 | 作用 | 要求 |
| --- | --- | --- |
| `backend/backups/` | 主备份，给日常回滚用 | 与数据库同机 |
| 第二块盘 / NAS / 移动硬盘 | 防灾备份 | 每日同步一次（见下） |
| （可选）对象存储 | 异地 | 每周一次；注意数据敏感，需加密 |

同步用系统自带工具即可，不必引入新依赖：

```powershell
# Windows：把当日备份同步到 D 盘（任务计划里同样这一步）
robocopy C:\nova-erp\backend\backups D:\backup\nova-erp /MIR /R:1 /W:1
```

```bash
# Linux：rsync 增量同步
rsync -a --delete /opt/nova-erp/backend/backups/ /mnt/nas/nova-erp/
```

> `/MIR` 与 `--delete` 都是**镜像**语义：源目录删了目标也删。
> 这是刻意的 —— 保留策略由 `nova-ops` 统一管，同步工具不要有第二套规则。

### 2.6 校验与恢复演练（每月 1 次，写进日历）

备份不是「跑完了」就行，要证明「能恢复」：

```bash
# 1) 恢复到临时库（默认自动命名 <db>_restore_<时间戳>，不会盖掉生产库）
./nova-ops restore --config config.yaml --file backups/nova_inv_v5-20261018-100717.dump --yes

# 输出会自动核对：表数、sys_users / inv_products / inv_orders / inv_order_items 行数
#   ✓ 已恢复到 nova_inv_v5_restore_20261018_100726
#     23 张表 · 关键表行数 sys_users 2 · inv_products 9 · inv_orders 19 · inv_order_items 31
#     ! inv_orders 行数不一致：备份时 161，恢复后 159   ← 出现这种提示就要查

# 2) 抽查业务数据（可选，但建议）
#    用只读账号连临时库，随便打开一张旧单据核对金额

# 3) 删掉临时库
psql -d postgres -c 'DROP DATABASE "nova_inv_v5_restore_20261018_100726"'
```

恢复命令的三条安全设计，正是为了让「演练」变成一件随手能做的事：

1. 默认落到**新库**，不盖生产库；
2. 目标库已存在直接报错，**不自动 DROP**；
3. 恢复前校验 sha256，文件损坏时立刻失败，而不是写出一个「部分成功」的库。

### 2.7 计划任务

**Windows（本项目实际部署环境）**

```powershell
# 以管理员身份创建每日 22:00 的任务
schtasks /Create /TN "nova-erp backup" /SC DAILY /ST 22:00 /RU SYSTEM ^
  /TR "cmd /c cd /d C:\nova-erp\backend && nova-ops.exe backup --config config.yaml >> logs\backup.log 2>&1"
```

**Linux**

```cron
# /etc/cron.d/nova-erp-backup
0 22 * * * root cd /opt/nova-erp/backend && ./nova-ops backup --config config.yaml >> logs/backup.log 2>&1
30 22 * * * root rsync -a --delete /opt/nova-erp/backend/backups/ /mnt/nas/nova-erp/
```

> 计划任务用 **SYSTEM / root** 跑，但要确认它能读到 `config.yaml` 与备份目录。
> 更稳的做法是建一个专用的低权限系统账号，只给 `backups/` 的写权限。

### 2.8 可选升级：WAL 归档（RPO ≤ 1 小时时再上）

```conf
# postgresql.conf
wal_level = replica
archive_mode = on
archive_command = 'copy "%p" "D:\\pgwal\\%f"'   # Windows；Linux 用 cp
```

配套：每周一次 `pg_basebackup -Ft -z -D base`，与 WAL 一起构成「任意时间点恢复」。
**不做这步就别开 `archive_mode`** —— 归档目录写满会让数据库直接停止写入。

## 3. 数据清理

### 3.1 原则

清理的判据只有一条：**这份数据丢了会不会影响对账 / 追责**。

| 数据 | 处理 | 理由 |
| --- | --- | --- |
| 操作日志 `sys_operation_logs` | 保留 180 天 | 追责窗口通常一个考核周期；超过半年的「谁改了这个价」没人再查 |
| 登录日志 `sys_login_logs` | 保留 180 天，**锁定窗口内不删** | 见 §3.5 |
| 幂等键 `sys_idempotencies` | 过期后再留 7 天 | 过期即不可能被回放；留 7 天覆盖「过期前提交、过期后重试」 |
| 单据 / 明细 / 出入库 | **不按保留期自动删**，只能走业务清理（§3.7） | 这是账。删了库存与应收应付都对不上，且无法追溯 |
| 软删除的主数据（商品 / 客户 / 供应商） | **不自动物理删除**，只在体检里报告 | 它们被历史单据引用着；物理删掉后「这笔单卖的是什么」永久无解 |

> 「日志按保留期自动清」与「业务数据手工清」是两回事，前者可以进计划任务，
> 后者必须是有人看着确认的一次性动作 —— 见 §3.7。

### 3.2 命令

```bash
# 第一步：预演（默认行为，不删任何数据，只报会删多少）
./nova-ops cleanup --config config.yaml

#  清理模式：预演（不会删除任何数据）
#  对象       表                   删除边界     行数  批次  说明
#  操作日志   sys_operation_logs   2026-04-21   0     -     保留最近 180 天
#  登录日志   sys_login_logs       2026-04-21   0     -     已按账号锁定窗口兜底
#  过期幂等键 sys_idempotencies    2026-10-11   0     -     过期后再保留 7 天

# 第二步：确认行数与边界合理后，真删
./nova-ops cleanup --config config.yaml --apply
```

保留期在 `config.yaml` 里改，不用动命令：

```yaml
maintenance:
  op_log_days: 180
  login_log_days: 180
  idempotency_days: 7
```

### 3.3 为什么分批删

每批 5000 行（`--batch`）。一条 `DELETE` 删几十万行会：

- 长时间持锁，期间业务写入排队；
- 一次性写满 WAL，磁盘紧张时直接把库顶到只读；
- 留下大量死元组，表反而更膨胀。

分批之后每批都是毫秒级，中间业务无感。删完立刻 `VACUUM (ANALYZE)`：
日志查询几乎都带时间范围，统计信息陈旧会让「最近 7 天」走错执行计划。

> 不用 `VACUUM FULL`：它会重写整张表并持有排他锁，日志表再大也不值得为省几 MB 停机。

### 3.4 单次能删多少

日志表 100 万行、每批 5000、每批约 20 ms → 全部删完约 4 秒（不含 VACUUM）。
真到千万行级别才需要专门排窗口，本项目规模到不了，但分批逻辑让它即使到了也不会出事。

### 3.5 登录日志的坑（这不是理论问题）

登录失败日志不只是审计证据，还是 `auth.isLocked` 判定账号锁定的**计数来源**。
如果清理边界算错，把「5 分钟内」的失败记录删掉，就等于：

> 攻击者连续试错触发锁定 → 请求一次清理 → 锁定解除 → 继续试。

所以清理时的边界取「保留期」与「锁定窗口」中**更早**的那个：
`cutoff = min(now - 180天, now - 锁定秒数)`。
代码里有专门的单测（`TestResolveCutoffsRespectsLockWindow`），因为这个符号写反过一次 ——
写反的表现是「删掉 5 分钟前的所有日志」，平日完全看不出，出事时审计是空的。

### 3.6 长期归档（超过 2 年的单据）

不做自动归档。真需要时走这条手工路径：

1. 报表中心按日期区间导出 xlsx（已含明细），归档到文件服务器；
2. 人工确认导出文件能打开、行数对得上；
3. **不删库里的单据** —— 十几 MB 的数据不值得为它冒「对不上账」的风险。

数据量真的到了 GB 级（十年以上）再考虑按年分库，那时也应当先做归档表而不是删数据。

### 3.7 业务数据清理（不可逆）

日志清理按保留期进行，适合无人值守；**业务数据是另一回事** ——
「把今年的单据全清了、只留商品」这种需求真实存在（年底重开账、演示环境复位、
把系统交给下一个使用者），但它不可逆，所以单独做成一档一档确认的动作。

命令（`nova-ops reset`）与管理页（「系统运维 → 数据清理 → 业务数据清理」）能力完全一致：

```bash
# 预演：只报每张表会删多少，不删任何数据
./nova-ops reset --config config.yaml --scope inv_documents

# 真删：必须输入该范围专属的确认口令
./nova-ops reset --config config.yaml --scope inv_documents --confirm 确认清理单据 --apply

# 清单据的同时把规格库存归零（默认不动库存）
./nova-ops reset --config config.yaml --scope inv_documents --confirm 确认清理单据 --apply --reset-stock
```

三档范围：

| 范围 | 删什么 | 保留什么 | 确认口令 |
| --- | --- | --- | --- |
| `inv_documents` | 采购/销售/出入库单据与明细、收付款记录 | 商品、规格、单位、分类、客户、供应商、打印模板、系统框架 | 确认清理单据 |
| `inv_all` | 全部进销存业务表（含商品与往来单位档案） | 系统框架 | 确认清空进销存 |
| `database` | 全部进销存业务表 + 操作日志 + 登录日志 + 幂等键 | 系统框架（账号、角色、菜单、权限、部门、结构版本、升级记录） | 确认重置数据库 |

**「数据库重置」刻意不动系统框架**：账号/角色/菜单/权限删掉之后，正在跑的系统会立刻
失去登录与鉴权依据，现场看到的现象是「所有人都登不进去」，分不清是数据丢了还是系统坏了。
真要连框架一起清，请直接 DROP DATABASE —— 程序会重新建库并播种，
那才是「交还给下一个使用者」的正确做法。

三道闸门（代码里钉死，有测试）：

1. **24 小时内必须有备份**。没有回滚点不许动账；界面上「先备份」按钮就在旁边，
   而命令行要加 `--force` 才能跳过（危险，仅用于备份盘也坏了的极端情况）。
2. **确认口令与范围绑定**。三档口令互不相同，手滑点到「确认」跳不到更危险的档。
3. **一个事务**。全部删除要么都成要么都不成 —— 清到一半失败会留下
   「单据没了但收付款还在」的库，比不清更难查。
4. **白名单按档位判定**。运行时校验不只看「这张表是不是框架表」，
   还要看**当前是第几档**：`sys_operation_logs` / `sys_login_logs` / `sys_idempotencies`
   只在 `database` 档允许整表清空，换成「只清单据」这档就会被拒。
   平时清日志走 §3 的保留期清理，不走这一条路。

两个实现细节：

- **硬删 + 序号重置**：业务清理的目的就是回收空间与重置状态，软删只会把行留着继续占
  唯一索引与主键。表被清空后顺手 `setval` 把自增序列重置，下一单从 1 开始。
- **库存是可选项**：清单据时默认**不动** `inv_product_specs.stock`。
  重录单据的人要勾「同时清零」，刚盘点完的人不能勾 —— 这两种场景都存在，
  所以做成勾选框而不是替用户决定。

## 4. 系统升级

### 4.1 版本三元组

一次升级有三个版本，必须同时对齐，缺一个就会出现「页面和接口对不上」：

| 版本 | 在哪 | 怎么变 |
| --- | --- | --- |
| **程序版本** | `app.release`（`config.yaml`，建议构建时 ldflags 注入） | 换二进制，见 §4.3 |
| **结构版本** | `sys_schema_versions` 表 + 代码常量 | 改表结构时 `+1`，启动自动登记 |
| 前端版本 | `frontend/dist` 静态产物 | 整目录替换（文件名带 hash，浏览器自动拿新的） |

> `app.release` 缺省是 `dev`。它不只是给人看的：升级执行后**要拿它和目标版本比对**，
> 才知道这次升级到底生效没有（§4.7）。为 `dev` 时记录会一直停在「已执行待重启」，
> 这是刻意让它显眼，而不是静默显示成功。

### 4.2 结构版本闸门（本次新增）

`AutoMigrate` 只做「补齐」，它不知道方向。所以加了一张表 + 一道启动检查：

```sql
SELECT * FROM sys_schema_versions;
--  version |         applied_at         |                  note
-- ---------+--------------------------+----------------------------------------
--        1 | 2026-10-18 10:08:31+08  | 基线：框架 11 张表 + 进销存 12 张表
--        2 | 2026-10-18 11:37:00+08  | 新增 sys_upgrade_records：升级记录表
```

启动顺序（`internal/bootstrap`）：

```
连接数据库
  → 读库版本（表不存在则视为 0，不报错）
  → 库版本 > 程序版本 ? 拒绝启动
  → AutoMigrate（补齐结构）
  → EnsureIndexes / PatchData（索引与历史数据修补，均幂等）
  → 登记新版本
```

实测拒绝效果（把库版本手工改成 99 后启动旧程序）：

```
服务启动失败: 数据库结构版本 v99 高于当前程序支持的 v1：请升级程序，或用升级前的备份恢复。
旧程序连新库会读错字段，这不是「先跑起来再说」的问题
```

**改结构时的纪律**（写进 AGENTS.md）：

1. 改表结构 → `database.CurrentSchemaVersion` **+1**，并在 `schemaChanges` 写一句说明；
2. **只加不删不改名**：先发一版「不再读写该列」的代码，下一版再删列；
3. 数据修补一律登记到 `dataFixes`（幂等、可审计），不要临时敲 SQL。

### 4.3 升级 SOP（按顺序，别跳步）

| # | 动作 | 命令 / 检查点 | 失败怎么办 |
| --- | --- | --- | --- |
| 1 | 选窗口 | 业务空闲（午休 / 下班后），避免正在开单 | — |
| 2 | 记版本 | 记下当前二进制与 `check` 输出 | — |
| 3 | **体检** | `nova-ops check --strict` | 有告警先处理，别在带病状态下升级 |
| 4 | **备份** | `nova-ops backup --no-prune` | 备份失败 → **停止升级** |
| 5 | 停服务 | 停 `nova-erp.exe` | — |
| 6 | 换二进制 | 覆盖 `nova-erp.exe`（旧的留一份 `.bak`） | — |
| 7 | 启动 | 观察日志：应出现「数据库结构版本 vN → vM」与「HTTP 服务已启动」 | 启动失败 → 见 §4.4 |
| 8 | 冒烟 | 登录 → 打开采购单列表 → 开一张单 → 审核 → 查看详情 → 导出 | 失败 → 回滚 |
| 9 | 换前端 | 替换 `frontend/dist`，强制刷新（Ctrl+F5） | 前端可单独回滚，见 §4.5 |
| 10 | 观察 | 半小时内看日志有无 5xx / 慢查询；次日确认日志正常写入 | — |

**用管理页走同一条 SOP**（`/system/ops` → 系统升级页签）：页面上传升级包（自动校验
manifest 与 sha256）→ 点「升级前备份」（不备份就无法点「执行升级」）→ 输入「确认升级」
执行。执行动作是：后端二进制落位为 `<exe>.new`、前端产物原子切换（旧目录保留为
`.old.<时间戳>`）。**它不会替你覆盖正在运行的 exe** —— Windows 上系统也不允许，
所以最后一步永远是「停服务 → 换文件名 → 启动」。

#### 升级相关配置（`config.yaml` 的 `upgrade` 段）

| 配置 | 含义 | 缺省 |
| --- | --- | --- |
| `frontend_dir` | 前端产物目录，升级时**整目录替换** | 空 = 本次升级只含后端 |
| `staging_dir` | 升级包解压与落位的暂存目录 | `<可执行文件所在目录>/upgrade/staging` |

`frontend_dir` 是要被整个换掉的目录，所以启动时会拒绝三类值：文件系统根（`/` / `C:\`）、
进程工作目录、以及可执行文件所在目录**及其祖先** —— 配成这些值时，
升级的「把旧目录改名」这一步就把程序自己脚下的东西搬走了。宁可启动失败，
也不要等某次升级把系统搞挂。

冒烟必查这 6 项：**登录、单据列表、开单、审核（会写库存）、详情、导出**。
它们覆盖了「读、写、事务、跨表、文件生成」五类路径，任何结构变更的问题都会在其中暴露。

### 4.4 回滚矩阵

| 情况 | 库结构动了吗 | 回滚动作 | 数据影响 |
| --- | --- | --- | --- |
| 新程序起不来，未执行迁移 | 否 | 换回 `.bak` 二进制 | 无 |
| 已迁移，但页面/接口报错 | 是（只加了表/列） | 换回旧二进制 —— **闸门会拦**，需用备份恢复 | 丢失升级后的写入（升级窗口内通常没有） |
| 已迁移且写入了新数据 | 是 | **恢复升级前备份** + 换回旧二进制 | 丢失备份点之后的数据（这就是 RPO 的代价） |
| 只是前端白屏 | 否 | 换回旧 `dist` 目录 | 无 |

**注意第二行**：这正是闸门存在的意义。旧程序连新库时，`AutoMigrate` 不会报错，
它会安静地把「多出来的列」当成不存在，直到某个查询按旧字段名失败 —— 那时已经写入了脏数据。
所以「结构动过就别想着直接换回旧二进制」，老老实实恢复备份。

### 4.5 前端单独回滚

`frontend/dist` 是纯静态产物，回滚零风险：

```bash
mv frontend/dist frontend/dist.bak.20261018 && cp -r frontend/dist.old frontend/dist
```

前提是每次发布会留一份 `dist.bak.<日期>`（或在 CI 里保留最近 3 个构建产物）。
前端与后端必须**同批发布**：接口参数改名时，新前端配旧后端会直接 40000。

### 4.6 零停机升级（可选，本系统当前不需要）

单机单实例的 ERP 没有 7×24 要求，停机 5 分钟可接受。真要零停机，必须遵守三条兼容规则，
否则「同时跑两个版本」的窗口期一定出问题：

1. **先加后用**：新增列先允许 NULL，代码下一版才读它；
2. **不删不改名**：旧代码还在读旧列时不能删；
3. **约束后置**：新唯一索引等数据清洗完再建（并且用 `CONCURRENTLY`）。

### 4.7 升级包格式与升级记录

**升级包是一个 zip**，结构如下（文件名写在 manifest 里，不写死）：

```
manifest.json          # 必填：版本、结构版本门槛、文件清单与摘要
nova-erp-server.exe    # 后端二进制（名字随平台；不必与线上同名，执行时落位为 <当前exe>.new）
dist.zip               # 可选：前端产物压缩包（zip 顶层必须直接是 index.html）
```

```json
{
  "version": "1.3.0",
  "minSchemaVersion": 1,
  "notes": "本次升级说明，会带进升级记录",
  "backend":  { "file": "nova-erp-server.exe", "sha256": "…" },
  "frontend": { "file": "dist.zip",            "sha256": "…" }
}
```

上传时会逐项校验：zip 结构（不许嵌套目录）、manifest 必填项、**文件名必须是纯 basename**
（带路径就能越出暂存目录写文件）、以及每个文件的 sha256。摘要对不上直接拒绝 ——
「包在传输中半截」和「包被人改过」必须区分开。

**怎么打这个包**：不要手搓 zip 和摘要，用脚本一条命令生成（自动构建后端与前端、
逐个算 sha256、写 manifest）：

```bash
node scripts/build-upgrade-package.mjs --version 1.3.0
# 只发后端：  --backend-only
# 只发前端：  --frontend-only
# 带上结构版本门槛与说明：--min-schema 3 --notes "修复报表导出"
```

细节（含两条必须提前对齐的配置 `app.release` / `upgrade.frontend_dir`、
以及常见报错对照）见 [UPGRADE.md §6.2.1](./UPGRADE.md)。

请求体上限 512 MB，而且是在**读取阶段**就把连接掐断，不是收完再统计：
先 `FormFile` 再 `LimitReader` 的写法会让 gin 先把超过 32 MB 的部分落到临时文件，
一个「声明很小、实际一直发」的客户端足以把临时目录写满。

**升级记录**（`sys_upgrade_records`）一次升级一行，走完四个状态：

| 状态 | 含义 |
| --- | --- |
| `pending` | 计划已生成，等待执行 |
| `executing` | 执行中。执行前用「状态是 pending 才更新」抢占，并发点两次只有一次能进来；<br>重启时若发现记录停在这里，说明上次执行**中断**了，判为 `failed` |
| `applied` | 已执行（二进制落位 `.new`、前端已切换），**等待重启生效** |
| `success` | 重启后当前运行版本与目标版本一致，升级闭环。**纯前端包无需重启，执行完直接到这一步** |
| `failed` | 重启后版本不一致 —— 换了回去或根本没换，需要人来看 |

生效核对由启动流程自动完成（`FinalizeUpgrades`）：它比的是「现在这个进程的版本」
与记录里的目标版本，**只对 `applied` 的记录做**。纯前端包（`manifest` 里没有 `backend`）
不需要重启，也永远等不到版本变化，所以执行阶段就判为 `success` ——
否则每条纯前端升级都会被误标成失败。

> 为什么后端只落位 `.new` 而不直接覆盖：Windows 上替换正在运行的可执行文件会被系统
> 拒绝，Linux 上虽然能 unlink，运行中的进程仍持有旧 inode。两个平台的正确做法一样 ——
> 落位 `.new`，由重启完成替换。附带好处是回滚只需删掉 `.new`。

## 6. 故障处理

| 症状 | 最可能的原因 | 处置 |
| --- | --- | --- |
| 服务起不来，日志说「结构版本 vX 高于…」 | 用了旧程序连新库 | 换新程序；或恢复升级前备份后用旧程序（§4.4） |
| 服务起不来，「连接数据库失败」 | PG 服务没起 / 口令错 / 端口占 | `sc query postgresql-x64-17`；核对 `config.yaml`；`netstat` 看 5432 |
| 备份失败「找不到 pg_dump」 | PATH 里没有 PostgreSQL | 配 `backup.pg_dump_path`（Windows 常见 `C:\Program Files\PostgreSQL\17\bin\pg_dump.exe`） |
| 备份失败「server version mismatch」 | pg_dump 版本低于服务器 | 用同版本或更高版本的客户端（工具会自动挑最高版本，配置写死后需手动改） |
| 磁盘满 | 备份未轮转 / 日志未清理 | 先删旧备份（`--keep 5` 跑一次 backup 触发轮转），再 `cleanup --apply` |
| 误删了一条单据 | 软删除，数据还在 | `UPDATE inv_orders SET deleted_at = NULL WHERE order_no = '…'`（先备份） |
| 误删了整个库 | — | 恢复最近备份（§2.6 的 restore 但目标改为生产库名，需 `--force`），损失 = RPO |
| 清理后审计记录缺失 | 边界算错 / 手工 SQL | 恢复备份中的日志表：`pg_restore -t sys_operation_logs`（自定义格式支持单表恢复） |

## 8. 命令速查

```bash
# 备份（默认按配置轮转）
nova-ops backup --config config.yaml
# 升级前留档，不轮转
nova-ops backup --config config.yaml --no-prune
# 临时换目录 / 少留几份
nova-ops backup --config config.yaml --dir D:\backup\nova-erp --keep 10

# 恢复（必须 --yes；默认落到新库）
nova-ops restore --config config.yaml --file backups/xxx.dump --yes
# 指定库名
nova-ops restore --config config.yaml --file backups/xxx.dump --db nova_inv_v5_verify --yes

# 清理（默认预演）
nova-ops cleanup --config config.yaml
nova-ops cleanup --config config.yaml --apply --op-log-days 365

# 体检
nova-ops check --config config.yaml
nova-ops check --config config.yaml --strict --json

# 业务数据清理（不可逆；默认预演，--apply 才真删，要求 24 小时内有备份）
nova-ops reset --config config.yaml --scope inv_documents                      # 预演
nova-ops reset --config config.yaml --scope inv_documents --confirm 确认清理单据 --apply
nova-ops reset --config config.yaml --scope inv_all --confirm 确认清空进销存 --apply
nova-ops reset --config config.yaml --scope database --confirm 确认重置数据库 --apply
nova-ops reset --config config.yaml --scope inv_documents --confirm 确认清理单据 --apply --reset-stock
```

> 所有子命令都支持 `--config`；未给的参数一律取 `config.yaml` 里的默认值，
> 命令只覆盖「这一次想改的」，不做第二份配置。
