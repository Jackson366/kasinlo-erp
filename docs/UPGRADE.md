# nova-admin 后台系统独立升级方案

> 版本：v1.0（2026-10-12）
> 目标：让后台管理系统（框架 + 系统模块）可以**独立于业务模块单独升级**，
> 业务代码的堆叠不抬高框架升级的成本，框架升级也不强迫业务同步改造。

---

## 1. 问题定义

nova-admin 的定位是「可复用的后台管理底座」，业务（如进销存 invflow）以模块形式往上加。
没有边界约束时，升级会遭遇三类耦合：

| 耦合类型 | 典型症状 |
| --- | --- |
| **代码耦合** | 业务 handler 直接改 `internal/pkg` 里的通用函数；`pkg` 反过来 import 业务模块 |
| **数据耦合** | 业务迁移改了系统表结构；系统迁移假设业务表存在 |
| **依赖耦合** | 业务需要一个新库版本，与框架锁定的旧版本冲突，升级被业务绑架 |

本方案的目标是：**升级框架时，只要系统回归套件全绿就能发布，不需要业务代码参与；升级业务时，不触碰框架目录。**

## 2. 边界划分：什么是「后台系统」，什么是「业务」

### 2.1 目录契约（硬边界）

```
backend/
├── cmd/server/              # 框架：组装入口
├── internal/
│   ├── module/contract.go   # 框架：模块契约 MenuNode / Module / Build / Group（纯类型，不 import 具体模块）
│   ├── assembly/            # 框架：组装层（composition root）——全项目唯一 import 具体模块的地方
│   ├── authz/               # 框架：授权、数据范围（业务只准调用，不准修改语义）
│   ├── middleware/          # 框架：认证、限流、oplog
│   ├── oplog/               # 框架：操作日志基础设施
│   ├── pkg/                 # 框架：errcode/page/response/sheet/textutil/jwt/limiter/bind
│   ├── module/
│   │   ├── user|role|menu|dept|log|dashboard|auth/   # 框架：系统模块（每个含 module.go 自描述清单）
│   │   └── invflow|.../     # 业务：业务模块（每个业务一个子目录，准出规则见 §3）
│   ├── database/            # 框架：连接、时区、迁移入口
│   ├── router/              # 框架：遍历模块登记表挂路由（不 import 具体模块）
│   └── seed/                # 框架：内置角色/菜单/账号（业务 seed 单独文件，见 §4.2）
├── migrations/              # 框架：0001~N 系统迁移；业务迁移独立编号段（§4.1）
├── scripts/                 # 框架：check-module-boundary.sh（依赖方向门禁）等
└── test/                    # 框架回归套件（系统测试）+ 业务测试分文件
frontend/
├── src/
│   ├── api/                 # 系统 api 文件与业务 api 文件分目录（§5.2）
│   ├── components/          # 框架：通用组件（EChart、Pagination…）
│   ├── router/              # 框架：守卫与注册机制；业务路由全部走后端动态下发
│   ├── stores/ utils/ directives/  # 框架
│   └── views/
│       ├── system/ profile/ dashboard/   # 框架：系统页面
│       └── biz/...           # 业务：业务页面（一个业务一个子目录）
```

**判定规则（一句话版）：**

- 会出现在「内置菜单 seed」里的模块 = 后台系统；
- 只通过「业务菜单管理」挂上来的模块 = 业务。
- `internal/pkg`、`internal/authz`、`middleware` 只服务系统语义；业务要扩展行为时**提钩子**，不直接改。

**边界是怎么被编译器强制的（本方案的落地形态）：**

系统模块与业务模块都只实现同一份契约（`module.Module`），由 `internal/assembly` 汇总登记；
`router` 与 `seed` 只读登记表。于是「删掉一个业务模块」= 删目录 + 在组装层删一行，
框架其余部分 diff 为零 —— **边界不是靠自觉，是删不掉的反面：删得掉**。

### 2.2 三条铁律

1. **依赖方向单向**：`业务 → 框架` 永远合法；`框架 → 业务` 一次都不许出现。
   已经落地成一条命令（`scripts/check-module-boundary.sh`，改动框架层后必跑）：
   ```bash
   # 框架包不许 import 具体模块（internal/module/<任意子包>），出现即视为破坏
   bash scripts/check-module-boundary.sh
   ```
   它用「框架路径白名单 + grep `internal/module/<子包>`」判定，比逐个枚举业务模块名更强 ——
   **新增模块不必维护白名单**；排除 `internal/assembly/`（组装层本就是唯一该 import 具体模块的地方）
   与 `_test.go`。
2. **系统表与业务表不互相外键**：系统表（sys_*）只允许被业务表**引用**（业务表存
   user_id/dept_id），系统表永远不存业务表主键、不加指向业务表的 FK。
3. **框架不改业务行为**：框架升级 diff 里出现业务模块的文件 = 违规，
   反过来，业务 PR diff 里出现 `internal/pkg`、`middleware` 等框架目录 = 违规。

## 3. 业务模块的「准出清单」

业务模块要能随框架升级零成本搬家（甚至整个删掉），创建时必须满足：

- [ ] 只 import 框架层（`internal/pkg/*`、`authz`、`model` 基础类型），不 import 其他业务模块
      ——确需跨业务调用时走**接口注入**（在 wire/组装处把 A 业务的能力作为接口传给 B），
      不直接包引用
- [ ] 有 `module.go` 自描述清单（`Namespace` + `Register` + `Menus`），并在 `internal/assembly` 登记一行；
      框架其余包对它零引用（`bash scripts/check-module-boundary.sh` 必须无输出）
- [ ] 路由全部经 `route.go` 注册、由清单的 `Register` 带出，权限码走菜单表（动态下发），
      **不在前端写死路由**；菜单写在清单的 `Menus` 里，框架 `seed.go` 不出现业务菜单
- [ ] 数据表名带业务前缀（`inv_*`、`crm_*`），迁移文件放业务编号段（§4.1）
- [ ] 权限码用业务命名空间（`inv:order:create`），不冒用 `system:*`（契约校验会拦）
- [ ] 业务演示数据放独立文件 `internal/seed/biz_<name>.go`，由 `seed.Run` 显式调用；
      框架 seed 文件不出现业务名
- [ ] 有独立的业务回归测试文件，可整体删除而不破坏 `go test ./test/...`

## 4. 数据库分层升级

### 4.1 迁移编号分段

| 段 | 归属 | 示例 |
| --- | --- | --- |
| `0001~0999` | 框架系统表（sys_*） | `0007_add_token_epoch.sql` |
| `1000~1999` | 业务 A（invflow） | `1001_create_inv_orders.sql` |
| `2000~2999` | 业务 B | … |

- 框架升级只推进框架段；业务库只要框架段全部已应用，就能与新版框架对接。
- 业务迁移**禁止** `ALTER` 系统表；确需给系统表加业务字段的场景一律拒绝，
  改用业务侧新表关联。
- `upgrade_test.go` 覆盖「旧库 → 新版」的框架段升级路径（已有机制，保持）。

### 4.2 seed 分层

框架 seed（内置角色、内置菜单、admin/demo 账号）与业务 seed（业务演示数据）
分开：**内置菜单不再来自框架 seed 的手工清单，而是各模块 `module.go` 的 `Menus`**，
由 `seed` 遍历模块登记表统一播种；业务菜单树天然跟着业务模块走，不必另开 seed 文件。

幂等键从「手工 ID」换成「权限码（按钮）/ 路由名（目录、页面）」，兼容三态：
命中未删除记录 → 复用原 ID 且不覆盖字段；命中已软删记录 → 告警并跳过整棵子树（不复活）；
都不命中 → 新建（主键自增）。业务演示数据仍放 `internal/seed/biz_<name>.go`，自行幂等。

## 5. API 与前端分层升级

### 5.1 API 兼容策略

- 路由前缀 `/api/v1` 不变；**框架接口**（`/auth/*`、`/system/*`、`/profile*`、`/dashboard*`）
  的请求/响应结构变更属破坏性变更，必须：加字段不删字段、旧字段保留一个版本、
  `swagger_test.go` 断言不回退。
- **业务接口**（`/inv/*` 等）由业务自行版本化，框架不感知。
- 破坏性 API 变更的出口是**主版本号**（见 §6），小版本内只做向后兼容演进。

### 5.2 前端

- `src/api/` 分 `system/`（框架）与业务目录；框架页面的 api 调用类型定义与
  后端 swagger 保持同步。
- 业务页面全部通过动态路由下发，框架升级**不会**触碰业务页面文件；
  业务页面删除后框架照常启动（动态路由 404 兜底已有）。
- 通用组件（`Pagination`、`EChart`、`sheet` 导出等）是框架的公开契约：
  升级时 props/事件不破坏性变更；要破坏时先发 deprecation 警告一个版本。

## 6. 版本策略与升级 SOP

### 6.1 版本号

`config.yaml` 已有 `version` 字段，与 git tag 统一管理：

```
vMAJOR.MINOR.PATCH
- MAJOR：框架 API / 系统表结构破坏性变更（业务需要适配）
- MINOR：框架新能力（新权限点、新通用组件、数据范围增强），业务零适配
- PATCH：缺陷修复，业务零感知
```

框架升级（MINOR/PATCH）时业务代码**零改动**是硬承诺；做不到的改动进 MAJOR。

#### 6.1.1 版本路线（结合项目现状）

当前尚未打过任何 tag。结合成熟度（69 个测试、三套验证脚本、七批加固完成）：

| 版本 | 何时打 | 语义 |
| --- | --- | --- |
| **v0.9.0** | 现在 | 底座定版候选：功能完备、加固完成，但尚未经受真实业务检验。0.x 期间不承诺跨版本兼容 |
| **v1.0.0** | 条件触发，不拍脑袋 | 首个真实业务模块运行一个完整周期且无 P1 级回归 → 从此承诺严格 semver |
| 1.x | 持续 | MINOR = 新能力（业务零适配），PATCH = 修复；「业务零改动」成为硬承诺 |
| 2.0+ | 尽量少 | MAJOR 的节拍就是业务痛苦的节拍；能用 MINOR 演进的绝不进 MAJOR |

1.0 之前的重大重构用预发布标记（如 `v1.0.0-rc.1`），不占用版本号。

#### 6.1.2 MAJOR 判例表（什么改动必须进 MAJOR）

| 改动 | 归档 |
| --- | --- |
| 删响应字段 / 改响应结构 | **MAJOR**（加字段是 MINOR） |
| 系统表 `DROP COLUMN` / 破坏性 `ALTER` | **MAJOR**（这正是 §6.4 迁移红线选「只加不改不删」的原因） |
| 权限码格式、错误码语义变化（如 50100 → 409） | **MAJOR** |
| swagger 契约不兼容 | **MAJOR** |
| 新增接口 / 新增权限点 / 新组件 | MINOR |
| 缺陷修复、文档、测试 | PATCH |

边界情况的处理原则：**有行为变化但修的是错误行为 → PATCH**（如把本应 409 的
并发冲突从 50100 纠正过来，属缺陷修复；若业务已依赖 50100 做分支判断，那就是
MAJOR——发布前用 `CHANGELOG` 声明并给一个版本的过渡期）。

#### 6.1.3 版本落地动作（首次执行）

1. 建 `CHANGELOG.md`（Keep a Changelog 格式），把已完成的七批加固按
   Added / Changed / Fixed 归档为 0.9.0 条目
2. `config.yaml` 的 `version` 置为 `0.9.0`，与 tag `v0.9.0` 同步
3. 此后每次发版：CHANGELOG 先行 → version 字段 → tag 三者一致才算发布完成
   （加进 §6.2 SOP 第 5 步）

### 6.2 升级 SOP（框架侧发布）

```
1. 开分支 chore/upgrade-<ver>
2. 依赖升级（分两步，各自独立可回滚）：
   a. Go：go get -u ./...（只升级直接依赖；indirect 不主动动）
   b. npm：pnpm up element-plus vue vite 等（大版本逐个升，不一把梭）
3. 全量回归门禁（必须全绿才允许合并）：
   go vet && go test ./test/... ./internal/...
   npm run typecheck && npm run build
   bash scripts/check-module-boundary.sh   # 依赖方向门禁（框架不许 import 具体模块）
   node scripts/api-smoke.mjs        # 90 项接口断言
   node scripts/browser-verify.mjs   # 49 项结构断言
   node scripts/interaction-verify.mjs # 9 项交互断言
4. upgrade_test 补「上上个版本库 → 本版」迁移用例
5. bump config.yaml version → 打 tag → 合并
```

### 6.3 升级 SOP（使用方：把新版框架带给业务库）

```
1. 备份业务库
2. 部署新版后端：启动时自动应用框架段迁移（编号段隔离保证不会碰业务表）
3. 冒烟：api-smoke（系统接口段）+ 业务自身冒烟
4. 前端替换：框架产物直接覆盖，业务页面由动态路由带出
5. 观察一个业务周期（重点：oplog、authz 缓存、登录链路）
```

### 6.4 回滚

- **后端**：回退二进制即可——框架段迁移只加不改/不改不删（红线：
  迁移写法上禁止 `DROP COLUMN` / 破坏性 `ALTER`，字段废弃走「停写 → 下个 MAJOR 再删」），
  旧版二进制在新 schema 上可运行。
- **前端**：静态产物保留 N 个版本目录，切换软链即回滚。
- **数据**：业务表从未被框架迁移触碰，无回滚需求。

## 7. 已具备的基础（现状盘点）

| 机制 | 状态 | 对独立升级的贡献 |
| --- | --- | --- |
| 动态路由 + 菜单表 | ✅ | 业务页面与框架解耦 |
| 权限码全部走菜单表 | ✅ | 业务权限不写死在前端 |
| 模块契约 + 组装层（`module/contract.go` + `internal/assembly`） | ✅ | 业务模块可整块增删，框架 diff 为零 |
| 模块自描述清单（每个模块 `module.go`：`Namespace` + `Register` + `Menus`） | ✅ | 加菜单/权限不必再改框架 seed |
| seed 幂等键 = 权限码 / 路由名（兼容三态迁移） | ✅ | 重复执行安全，老库 ID 原样保留 |
| 依赖方向门禁 `scripts/check-module-boundary.sh` | ✅ | 框架反向依赖被脚本拦下 |
| 迁移文件按序号管理 | ✅ | 只需引入编号分段约定 |
| upgrade_test 旧库升级用例 | ✅ | 框架段升级有回归 |
| 三层浏览器验证 + 接口冒烟 | ✅ | 升级门禁现成 |
| `config.yaml version` 字段 | ✅ | 版本号落地处 |

**缺口（需按本方案补齐）：**

1. 业务模块目录约定（`module/<biz>/`、`views/biz/`）——尚无业务入驻，先立规矩
   （模块契约已就位，业务模块现在就能按 §3 准出清单落地）
2. 迁移编号分段——框架段未用满 999 时提前预留即可
3. ~~CI 依赖方向检查~~ —— **已落地**：`scripts/check-module-boundary.sh` 已进入提交前检查清单
   （GUIDE §3.7），契约本身另由 `internal/module/contract_test.go` 的 4 个用例
   （含 10 个「该拒绝的清单」子用例）兜住

## 8. 风险与限制

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 边界逐渐被侵蚀 | 赶工时业务顺手改框架最常见 | CI grep 门禁 + PR diff 检查清单 |
| 数据范围被业务绕过 | 业务自写查询漏套 ApplyLog | 新业务模板里带 scope 示例；code review 红线 |
| swagger 契约漂移 | 框架接口改了注解没同步 | swagger_test 已钉；升级 SOP 必跑 |
| seed 幂等破坏 | 业务 seed 写成「表空才插」 | 沿用按 ID 补齐模式，进准出清单 |
| 大版本升级仍需业务适配 | MAJOR 无法完全避免 | 变更日志列「业务适配指南」章节 |

## 10. 复杂性权衡（这套方案到底贵不贵）

**结论：运行时零成本，流程少量成本，换来的是升级解耦——净效果是降复杂性。**
本质是用廉价的前置约定，换昂贵的后置解耦；真正昂贵的不是这些清单，
而是没有边界时「改一行框架代码要在 N 个业务模块里找影响面」。

| 维度 | 增量 | 说明 |
| --- | --- | --- |
| 运行时代码 | ≈ 0 | 无新服务、新中间件、新代码路径，方案只有约定与门禁 |
| 构建/CI | 一条脚本 | 秒级；误报（注释命中）人工判断 |
| 心智负担 | 少量、持续 | 业务模块对照 6 项准出清单；测试两条新约束（不碰种子数据、异步断言轮询） |
| 升级流程 | 6 步 SOP | 换来「依赖升级不被业务绑架」 |
| 换回来的 | 大幅下降 | 业务与框架纠缠后的解耦成本、依赖版本冲突、全量回归 |

**三个真实代价与缓解（诚实清单）：**

| 代价 | 缓解 |
| --- | --- |
| 早期空转：迁移分段、准出清单在首个业务入驻前是纸面规定 | 接受——规矩要经真实业务检验后再修订，属正常迭代 |
| 门禁误报：grep 命中注释也算违例 | 人工复核；有业务后可换 `go list -deps` 依赖闭包分析 |
| SOP 纪律：六步跳任何一步，「业务零适配」承诺即失效 | 门禁脚本化（能自动跑的绝不靠自觉） |

**YAGNI 分级（何时做何事）：**

- 现在就做（零成本）：目录契约、编号约定、版本号与 tag
- 首个业务入驻时：CI 硬门禁、准出清单首次实战校准
- v1.0 时：演练 §6.2 SOP 全流程 + 回滚演练
